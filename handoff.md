## User-visible symptoms and diagnosis

### 1. `The self-hosted search stack is temporarily unavailable (redlib)`

This message is generated by the application, not by the model. The flow is:

1. `searchSelfHosted()` starts SearXNG, Redlib, MediaWiki, and Miniflux in parallel.
2. Each provider is wrapped in `Promise.allSettled()`.
3. Rejected providers are recorded in `failedProviders`.
4. If the fulfilled providers return no candidates, `SearchUnavailableError` is thrown.

The relevant code is `app/server/search/search-service.ts:48-78`. The message is
slightly misleading: `redlib` in the message means Redlib rejected, but the
other providers may simply have returned empty arrays. It does not prove that
every provider was unreachable.

Live evidence:

- `wowzerbowser-redlib-1` was running Redlib `v0.36.0`.
- The Redlib container had restarted 1,148 times.
- The adapter's request to `/search?q=Weather+Cup+Magcargo...` returned HTTP 404.
- Redlib logs repeatedly showed Reddit HTTP 403 responses and OAuth client 401s.
- The container healthcheck was green because it only probes `/`, not the search endpoint.

The provider code assumes that `/search` exists and that its result HTML
contains post links matching `/\/r\/[^/]+\/comments\//`. See
`app/providers/search/redlib-search-adapter.ts:21-52`.

### 2. SearXNG is green but the app requests the wrong HTTP method

The current adapter sends:

```text
GET /search?q=...&format=json&categories=...&pageno=1
Accept: application/json
```

See `app/providers/search/searxng-search-adapter.ts:14-26`.

On the live SearXNG instance, that request returned HTTP 200 with an HTML
results page. The SearXNG JSON API returned JSON when the same query was sent
with POST form data. Therefore the current adapter eventually fails in
`response.json()` with an HTML parsing error, even though the HTTP status is
200.

The SearXNG healthcheck has the same blind spot: it sends a GET request and
only checks for status 200. It therefore reports healthy for an HTML response
that the application cannot parse. See `compose.yaml:93-119`.

The live SearXNG logs also showed upstream instability:

- Brave: too many requests / suspended.
- Google CSE: unusual traffic / suspended.
- DuckDuckGo: connection timeouts.
- Startpage: CAPTCHA suspension.
- Wikipedia was the only consistently responsive engine during the check.

The immediate application fix should use POST for SearXNG and make the
healthcheck validate a JSON response, not just an HTTP status.

### 3. Irrelevant Wikipedia results

The transcript displayed pages such as Major League Soccer and FC Bayern while
the user was asking about Pokémon Weather Cup. Those URLs are consistent with
the MediaWiki/Wikipedia fallback rather than a useful web result.

The current ranking in `app/server/search/search-service.ts:26-45` uses only:

```text
provider weight / (30 + provider rank)
```

It does not score whether the title or snippet is relevant to the query. When
SearXNG's external engines are degraded, MediaWiki can supply unrelated or
weakly related pages and still be returned as successful search results.

The next implementation must make this behavior explicit. Recommended policy:

- Keep MediaWiki as a strong provider for `reference` searches.
- Do not silently use it as a web-wide fallback for `general`, `news`, or
  `community` searches unless the result passes an explicit relevance check.
- Preserve valid results from healthy providers when another provider fails.
- Report “no results” separately from “provider unavailable”; include failed
  provider names only as diagnostic detail.

### 4. `Direct page request failed with status 404/403`

These errors came from guessed public URLs, including guessed PvPoke JSON
paths and blocked GO Hub pages. They are expected destination responses, not
evidence that the page tool itself is broken.

`extractFirecrawl()` first calls local Firecrawl and then falls back to direct
HTML extraction if Firecrawl fails. The direct fallback intentionally raises
for non-2xx responses at `app/providers/research/research-page-adapters.ts:60-94`.
The Firecrawl-to-direct fallback is at lines 97-123.

Do not make `fetch_page` treat 404 or 403 content as valid evidence. The model
should stop guessing undocumented URLs, search for a real result URL, and
fetch that URL. If better diagnostics are desired, preserve both the Firecrawl
failure and direct-fetch failure in the returned error, but retain the current
security and status handling.

### 5. `web snippet is too long`

This was a real replay-validation bug and is already fixed on `main`.

- `lib/chat-citations.ts:1` defines the shared maximum as 1,500 characters.
- `sourceForUrl()` truncates snippets to that shared maximum at line 107.
- Before commit `b49384f`, `lib/chat-protocol.ts` replay validation still used
  a 1,200-character literal for search and page snippets.
- A live tool result could therefore succeed, but the next user message could
  fail when the prior assistant tool trace was replayed.

The current replay validator uses `CHAT_SOURCE_SNIPPET_MAX_LENGTH` at
`lib/chat-protocol.ts:759-761`. The regression test is
`tests/server-behavior.test.mjs:221-267` and passes.

If this error is still seen after deployment, verify that the running web
image contains `b49384f` and inspect whether an old persisted assistant trace
contains a snippet longer than the current protocol limit.

## Files and line regions to touch

### SearXNG adapter and healthcheck

Primary files:

- `app/providers/search/searxng-search-adapter.ts:14-40`
- `compose.yaml:93-119`
- `tests/search-stack.test.mjs:77-99`
- Add or extend a focused test near the SearXNG tests; do not rely only on the
  existing mock, which currently returns JSON regardless of request method.

Required changes:

1. Build the existing query parameters as URL-encoded POST form data.
2. Send `POST /search` with `Content-Type:
   application/x-www-form-urlencoded` and `Accept: application/json`.
3. Keep `q`, `format=json`, `categories`, `pageno`, and optional `time_range`
   semantics unchanged.
4. Check the response content type before calling `response.json()` and return
   a provider-specific error when SearXNG returns HTML.
5. Update tests to assert method, body, headers, and JSON parsing. Add a test
   proving that an HTML 200 response is rejected instead of being treated as
   valid JSON.
6. Update the Compose healthcheck to make the same POST request and parse a
   JSON response. A 200 HTML page must fail the healthcheck.
7. Replace `docker.io/searxng/searxng:latest` with a tested immutable image
   digest so a future SearXNG default-method change cannot silently break the
   adapter.

Do not “fix” this by merely adding a broader HTML parser. The provider contract
is JSON, and accepting the UI page would hide configuration/API regressions.

### Redlib adapter, availability, and deployment image

Primary files:

- `app/providers/search/redlib-search-adapter.ts:9-52`
- `compose.yaml:121-143`
- `.env.example:45-58`
- `tests/search-stack.test.mjs:8-26`

Required investigation and change:

1. Confirm the supported search route and response shape for the exact Redlib
   image that will be deployed. The current live `v0.36.0` image returns 404
   for the adapter's `/search` request, so do not assume the route is valid.
2. Either update the adapter to the supported route/HTML structure and add a
   fixture for it, or disable Redlib search until a supported route is
   available. Do not silently turn a 404 error page into zero results.
3. Keep non-2xx responses as provider failures, but include the status in the
   provider log so the search service can distinguish route mismatch, upstream
   blocking, and an empty result page.
4. Replace `quay.io/redlib/redlib:latest` with a tested immutable digest.
5. Improve the Redlib healthcheck so it detects the capability required by the
   adapter, not merely that the root page returns an HTTP response. If the
   supported search route itself depends on Reddit availability, document that
   dependency and avoid treating a green root probe as search readiness.
6. Add tests for HTTP 404/403, an upstream-error HTML page, and a valid search
   result page. Preserve the existing public Reddit URL normalization test.

The Redlib logs show that image/route compatibility is only part of the
problem: Reddit is also returning 403 and OAuth setup is returning 401. If the
chosen Redlib version cannot access Reddit reliably from homelab, the correct
behavior is a clearly reported unavailable provider, not a restart loop or
irrelevant fallback results.

### Aggregation, error semantics, and result quality

Primary files:

- `app/server/search/search-service.ts:18-78`
- `app/server/agent/web-tools.ts:114-139`
- `app/providers/search/mediawiki-search-adapter.ts`
- `tests/server-behavior.test.mjs:186-218`
- Add focused aggregation tests beside `tests/search-stack.test.mjs` or in a
  new `tests/search-service.test.mjs`.

Required behavior:

1. Track provider state as at least `fulfilled-with-results`,
   `fulfilled-empty`, and `rejected`.
2. If at least one provider has candidates, return candidates and log partial
   failures. Do not convert a partial outage into a total error.
3. If every provider is empty or rejected, return an error that distinguishes
   “no results” from “search providers unavailable”. Include rejected provider
   names, but do not claim the entire stack is unavailable when providers only
   returned empty arrays.
4. Prevent MediaWiki results from becoming general-purpose web results solely
   because other providers are broken. Use the recommended focus policy above
   or implement and test a clear lexical relevance gate.
5. Add a fixture reproducing the MLS/Bayern-style irrelevant Wikipedia output
   and assert that it is not returned for a specific Pokémon query in a
   non-reference focus.
6. Keep repository/database access out of this logic; provider adapters remain
   responsible for provider-specific HTTP and parsing behavior.

Do not expose raw provider stack traces or credentials in the tool result. The
user-facing error should remain concise; detailed provider status belongs in
server logs and, if needed, bounded diagnostic metadata.
